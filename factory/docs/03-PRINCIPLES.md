App Factory — Engineering Principles
These principles are architectural constraints.
They are not suggestions.
When implementation pressure conflicts with a principle, the conflict must be explicitly identified and resolved through a documented architectural decision.
P-001 — Single Source of Truth
There must be one authoritative implementation for lifecycle state and lifecycle transitions.
The dashboard, CLI, agents, workflows, and integrations must not independently implement state-transition logic.
P-002 — State Changes Only Through the Service Layer
No agent, CLI command, HTTP handler, n8n workflow, or UI component may directly mutate lifecycle state.
All state mutations must pass through the authoritative service layer.
P-003 — Human Approval Cannot Be Simulated
A HUMAN approval must be represented by an authenticated/authorized human actor.
The following are never equivalent to human approval:

* agent output
* model output
* automated test success
* webhook
* scheduled job
* CLI automation
* system actor
* "approved": true generated by an LLM

P-004 — Agents Reason; Services Execute
Agents should decide what they want to accomplish.
Deterministic services should execute actions.
Example:

```text
Agent:
"Run the Android test suite."

        ↓

Tool request

        ↓

Permission validation

        ↓

Test service

        ↓

Actual execution

        ↓

Structured result

```

An agent should not bypass the service/tool boundary merely because it can generate shell commands.
P-005 — Least Privilege
Every agent and tool must receive only the permissions necessary for its task.
Default permission is DENY.
Permissions must be explicitly granted.
P-006 — Fail Closed
When authorization, validation, state, schema, or security checks fail, the system must stop rather than guessing.
P-007 — Validate LLM Output
LLM output is untrusted input.
Important outputs must be:

1. parsed
2. schema-validated
3. semantically validated where required
4. rejected when invalid

Never assume an LLM followed the requested format merely because its response looks plausible.
P-008 — Never Invent Missing Data
If required information is unavailable, the system must represent the information as unavailable.
It must not fabricate:

* research evidence
* metrics
* competitor information
* test results
* security results
* API responses
* user feedback
* financial values
* publication status

P-009 — Evidence and Claims Must Be Separated
The system should distinguish:

```text
FACT
EVIDENCE
CALCULATION
ASSUMPTION
AGENT ANALYSIS
RECOMMENDATION

```

A recommendation must not be stored as factual evidence.
P-010 — Deterministic Logic Stays Deterministic
Use normal software for deterministic operations.
Examples:

* state transitions
* schema validation
* calculations
* permission checks
* budget checks
* file operations
* hashing
* test execution
* artifact validation

Do not ask an LLM to perform a deterministic operation when conventional code can do it reliably.
P-011 — Bounded Autonomy
Every autonomous loop must have explicit limits.
At minimum:

* maximum iterations
* timeout
* maximum token/model budget where applicable
* maximum external calls
* failure threshold

P-012 — No Silent Failure
Errors must not disappear.
The system must record failures with enough information to diagnose them.
P-013 — No Silent Recovery
Automatic recovery is allowed only when the recovery behavior is explicitly defined.
A system must not silently change architecture, permissions, state, or strategy to make an operation appear successful.
P-014 — Every External Side Effect Is Auditable
Actions such as:

* Git push
* release creation
* publishing
* advertising
* spending
* external API mutation
* deletion

must generate an audit event.
P-015 — Separate Planning from Execution
For consequential operations:

```text
PLAN
 ↓
VALIDATE
 ↓
APPROVE if required
 ↓
EXECUTE
 ↓
VERIFY
 ↓
AUDIT

```

Do not combine all six steps into an opaque agent call.
P-016 — Build Success Is Not Product Success
A successful compilation does not mean an application is ready for release.
Release readiness requires all applicable quality gates.
P-017 — Security Is a Pipeline Stage
Security checks must be integrated into the lifecycle.
Security must not depend solely on an agent remembering to perform a security review.
P-018 — Distribution Is Part of Product Engineering
An application is not considered complete merely because an AAB exists.
Distribution, measurement, and user acquisition must eventually be represented in the lifecycle.
P-019 — Cost Is a First-Class Resource
Model calls, compute, advertising, APIs, storage, and other paid resources must be treated as bounded resources.
The system should know:

```text
estimated cost
actual cost where available
budget
remaining budget

```

P-020 — No Unbounded Agent Shell Access
Agents must not receive unrestricted host shell access by default.
Commands should be executed through controlled tools or isolated execution environments.
P-021 — Sandbox Untrusted Work
Generated code, external repositories, downloaded artifacts, and untrusted inputs must be treated as potentially hostile.
Execution should occur inside appropriate isolation boundaries.
P-022 — Reproducibility Matters
Factory operations should record enough context to reproduce or diagnose important results.
Relevant inputs, versions, configuration, model information, and artifacts should be retained.
P-023 — Prefer Small Composable Components
The factory should use small services, agents, tools, and workflows with explicit interfaces.
Avoid giant classes, giant agents, and giant orchestration functions.
P-024 — Avoid Duplicate Sources of Truth
Do not maintain competing implementations of:

* lifecycle state
* permissions
* schemas
* business rules
* cost rules
* configuration
* audit events

If two components need the same information, expose a shared authoritative interface.
P-025 — Documentation Is Part of the System
Architecture-changing implementation work must update the relevant documentation.
Documentation that contradicts production behavior must be corrected.
P-026 — Tests Protect Architecture
Tests should verify not only feature behavior but architectural invariants.
Examples:

* agent cannot approve its own work
* illegal state transition is rejected
* unauthorized tool call is rejected
* invalid schema is rejected
* budget overflow is rejected
* failed build cannot become release candidate
* audit event is generated for required side effects

P-027 — Do Not Over-Engineer Before Evidence
Start with the simplest architecture that satisfies the current requirements.
Add infrastructure when there is a demonstrated requirement for it.
P-028 — Backward Compatibility Matters
Existing working functionality must not be casually rewritten.
Before modifying a subsystem:

1. understand the current behavior
2. identify dependencies
3. preserve existing contracts where possible
4. add/update tests
5. make the smallest safe change

P-029 — Phase Boundaries Are Real
When implementing a phase, do not silently implement unrelated future functionality.
Future requirements may be documented as interfaces or TODOs, but they should not become accidental scope.
P-030 — The Factory Must Be More Reliable Than Its Agents
Agents will make mistakes.
The factory architecture must assume this.
The state machine, schemas, permissions, budgets, validation, tests, audit logs, and approval gates exist specifically because an LLM cannot be treated as inherently reliable.
Final Engineering Rule
When uncertain:

```text
DO NOT GUESS.

Inspect the existing system.
Check the relevant specification.
Validate assumptions.
Prefer deterministic mechanisms.
Ask for clarification when a required decision cannot be established from evidence.

```

The goal is not maximum autonomy.
The goal is controlled, observable, repeatable autonomy.
