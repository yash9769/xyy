Factory Observability Architecture
1. Purpose
Observability allows the operator to understand what the factory is doing, why it is doing it, and where it failed.
A system that is autonomous but opaque is difficult to trust and difficult to debug.
2. Core Principle
Every important autonomous action should be explainable through state, events, evidence, and execution history.
3. Observability Domains
The factory should expose visibility into:

1. lifecycle state;
2. workflows;
3. agents;
4. models;
5. tools;
6. builds;
7. tests;
8. security;
9. releases;
10. distribution;
11. costs;
12. failures;
13. approvals.

4. Three Primary Signals
The target observability architecture should use:
Logs
Detailed execution records.
Metrics
Quantitative measurements.
Traces
Relationships between operations across the factory.
These should complement the existing audit log rather than replace it.
5. Logs
Operational logs may include:

* workflow start/end;
* tool invocation;
* agent execution;
* build output;
* test results;
* errors;
* retries.

Operational logs and audit logs have different purposes.
Audit logs establish accountability.
Operational logs support debugging.
6. Metrics
Useful factory metrics include:
Workflow

* workflows started;
* workflows completed;
* workflows failed;
* workflow duration.

Agents

* runs;
* failures;
* latency;
* token usage;
* cost;
* retries.

Tools

* calls;
* failures;
* latency;
* blocked calls.

Engineering

* build success rate;
* test failure rate;
* security findings;
* release-candidate rate.

Cost

* model cost;
* compute cost;
* application cost;
* distribution spend.

7. Tracing
A workflow should have a traceable execution path.
Example:

```text
Workflow: APP-042

  ResearchAgent
       ↓
  OpportunityAnalysisAgent
       ↓
  Human Approval
       ↓
  ProductAgent
       ↓
  CodingAgent
       ↓
  BuildTool
       ↓
  TestTool
       ↓
  SecurityTool
```

The operator should be able to inspect this chain.
8. Correlation IDs
The factory should propagate identifiers such as:

```text
workflow_id
application_id
task_id
agent_run_id
tool_execution_id
correlation_id
```

This enables cross-component debugging.
9. Agent Observability
Agent runs should expose:

* agent type;
* model;
* task;
* duration;
* result;
* failure;
* tool usage;
* cost;
* retry count.

Do not expose sensitive internal content unnecessarily.
10. Model Observability
The model router should eventually track:

* provider;
* model;
* request count;
* latency;
* failures;
* estimated/actual cost;
* structured-output failures;
* fallback frequency.

This enables informed routing decisions.
11. Tool Observability
For each tool:

```text
requested
authorized
started
completed
failed
blocked
```

The distinction between requested and executed is important.
A tool request being generated by an agent does not mean that the tool actually ran.
12. Workflow Timeline
The dashboard should eventually provide a timeline.
Example:

```text
09:00  Research started
09:03  Research completed
09:04  Opportunity analysis completed
09:05  Human approval requested
09:17  Human approved
09:18  Build started
09:21  Build blocked
```

This makes autonomous behavior inspectable.
13. Bottleneck Detection
Observability should help identify bottlenecks.
Examples:

* research consumes excessive time;
* model retries are high;
* build failures dominate;
* approval queue is growing;
* security scans are slow;
* distribution is blocked.

The factory may recommend optimization based on these measurements.
14. Alerting
Important operational conditions should generate alerts.
Examples:

* repeated workflow failure;
* budget exhaustion;
* security incident;
* corrupted state;
* stuck workflow;
* external service outage.

Alerting thresholds should be explicit.
15. Dashboard
The future dashboard should provide views such as:
Overview
Current factory health.
Action Required
Human decisions.
Applications
Lifecycle and health.
Workflows
Execution history.
Agents
Agent performance.
Costs
Resource consumption.
Failures
Current and historical failures.
Audit
Authoritative event history.
16. Observability and Privacy
Logs and traces can contain sensitive information.
The factory should apply:

* redaction;
* access controls;
* retention policies;
* secret filtering;
* minimum necessary data collection.

Never log:

* API keys;
* passwords;
* private signing keys;
* authentication tokens.

17. Current Implementation
The existing factory already provides:

* dashboard visibility;
* activity log;
* state information;
* audit history.

The target observability system should extend these capabilities without replacing the authoritative state machine or audit log.
18. Non-Goals
This document does not require immediate:

* enterprise observability platforms;
* distributed tracing infrastructure;
* full telemetry ingestion;
* AI-powered anomaly detection.

The architecture should remain implementable incrementally.

### §4/§5/§6/§7 — Logs, metrics, traces: none exist as a distinct layer

This document is explicit that logs/metrics/traces should **complement** the audit log, not be inferred from it. Today there is no such complementary layer at all:
- **Logs**: no operational log file or stream exists distinct from the audit log. This session's own tool-call transcript (Bash command output, WebSearch results) is the closest analogue, but it is not persisted anywhere in the repository — it exists only within this conversation.
- **Metrics**: zero factory metrics (workflow counts, agent latency, build success rate, cost) are computed or stored anywhere. The dashboard's stat cards (`counts.total`, `counts.awaitingApproval`, etc.) are the one exception — these *are* real, computed metrics, just narrowly scoped to opportunity-lifecycle counts (`store.js`'s `counts()` function), not the broader engineering/cost/agent metrics this document's §6 lists.
- **Traces**: no `workflow_id`/`agent_run_id`/`tool_execution_id`/`correlation_id` exists anywhere (per `25-AUDIT-LOGGING.md`'s reconciliation of the same gap from the audit angle) — there is nothing to trace a request through beyond the shared `opportunityId` field.

### §8 Correlation IDs — same gap as `25-AUDIT-LOGGING.md`, not re-litigated

Already covered in detail in that document's reconciliation: `opportunityId` is the only correlation mechanism today, sufficient while every entity in the factory is an opportunity or its derived app, insufficient once builds/tests/releases become independently-tracked entities.

### §9/§10/§11 — Agent, model, tool observability

**None exist**, for the same root reason each of docs 07/08/09 already established: no agent runtime, model router, or tool layer exists to instrument.

### §12 Workflow timeline — partially real, informally

**The Activity Log page is, in substance, a timeline** — `app.js`'s `renderActivity()` renders every audit entry with a human-readable timestamp, actor, action, and state transition, newest-first. It is missing this document's specific example's granularity (no "Research started" / "Research completed" entries exist, because research isn't a tracked, timed operation — only its *outcome*, a state transition, is recorded) and it is global rather than filterable to one opportunity's own timeline.

### §13/§14 — Bottleneck detection, alerting

**Neither exists.** With one opportunity ever processed, there is no meaningful pattern to detect a bottleneck from, and zero alerts of any kind have ever been generated by the factory itself (as opposed to this session's own judgment flagging the toolchain block in prose).

### §16 Privacy in logs/traces

**Not applicable yet in the negative sense — nothing has leaked, because there is no log/trace stream yet to leak from.** The one place this matters today, the audit log itself, has been checked and contains no secrets (consistent with `12-SECURITY.md`'s `gitleaks` scan covering the whole repository, `factory/state/` included).

### §17/§18

**Accurate as written** — this document's own current-implementation summary matches what was found here independently. No enterprise observability platform, distributed tracing, or anomaly detection was built or claimed.

### Summary

Two of thirteen observability domains (lifecycle state, approvals) are genuinely well-covered by the existing dashboard and audit log; everything requiring an agent, model, tool, build, test, security, distribution, or cost record to observe is unobservable because that underlying record doesn't exist yet — this is the same root cause identified across nearly every document in this series (07 through 24), now confirmed once more from the specific angle of "can an operator actually see this happening." No logs, metrics, traces, or new dashboard view was implemented while writing this document.
